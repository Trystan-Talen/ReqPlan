# 从 PRD（产品需求文档）到需求、任务与排期（星河研发台）

目标：用户把产品需求文档交给你，你在授权范围内交还一套**能直接用来管理进度**的提议、已确认需求、任务和排期，写入星河研发台，并如实汇报谁排到哪天、哪些节点赶不上、哪些假设需要确认。待确认的内容先进入提议，研发计划与承诺交付日期分别处理。

所有读写都通过 `xinghe`（星河命令行）完成，不直接改数据库。先运行 `xinghe --help`（帮助）和 `xinghe schema`（字段与规则说明），确认使用 0.4.0 或支持相同行为的更新版本。

## 硬规则

1. **不猜编号。** 项目、成员、提议、需求、文档的编号都要从 `project list`（项目列表）、`project members`（项目成员）、`proposal list`（提议列表）、`requirement list`（需求列表）、`document list`（文档列表）的输出里取。
2. **遇到下面五件事必须停下来问用户**，不要自己决定：
   - 文档对应哪个项目。一份文档可能要拆成几个项目，比如一份算法方案同时对应「评估方」和「执行方」两个项目。
   - 成员分工：谁负责哪个专业方向。项目成员只记录了角色（主开发 / 开发 / 测试），没有专长。规划文档如果写了「工程师 A / B / C」，要问清楚分别对应哪个账号。
   - 多个项目时间重叠时，先保哪个。
   - 需求清单：导入前把需求表给用户过目。
   - 写入排期前：把 `plan preview`（任务规划预览）的结论给用户看，尤其是超期和超载。
3. **提议与已确认需求分开录入。** 尚待确认的内容用 `proposal create/import`（创建 / 导入提议），进入“待评估”；用户明确确认且背景与目标、验收标准完整后，用 `proposal approve`（确认转需求）纳入“已确定”需求。已确认清单可用 `requirement create/import`（创建 / 导入需求）直接录入。“未确定 / 待评审”是历史早期记录，也从提议入口评估，不再按旧状态链更新需求。
4. **如实报告超期和超载。** 不要为了排进节点而悄悄压缩工时、删减范围或假设加班。只有规划文档写明了加班安排，才能在冲刺期提高每日产能，并在汇报里写明。
5. **写入前确认目标环境。** 用 `xinghe config show --profile <环境>`（查看环境配置）核对地址，并向用户说明「将写入 <地址>」。正式环境和本机环境分别用不同的 profile（环境配置），例如 `production`（正式环境）、`local`（本机环境）。第一次在正式环境操作时，建议先在本机环境完整演练一遍。
6. **写操作先预览。** 用相应导入命令的 `--dry-run`（预检）和 `plan preview`（任务规划预览）核对后，取得用户同意再写入。已有明确授权时无需重复询问。
7. **承诺排期独立保留。** 任务规划不自动创建或改写需求承诺日期、基线。研发阶段由后端根据任务自动同步，不通过修改需求状态手动推进。需要承诺日期时，单独说明建议区间并执行明确的承诺排期操作。

## 第 0 步：准备

```sh
xinghe config show --profile <环境>          # 确认连的是哪个平台
xinghe auth me --profile <环境>              # 确认登录账号
xinghe project list --profile <环境>
xinghe project members <项目编号> --profile <环境>
xinghe schedule list --kind requirement --profile <环境>   # 了解现有排期
```

登录由用户在自己的终端完成：`xinghe auth login --username <账号>`。不要索要或转述密码。

**账号权限决定能做哪一步：**

| 步骤 | 需要的项目角色 |
| --- | --- |
| 创建提议，补充本人待评估 / 待补充的提议 | 产品经理、主开发、开发、测试或管理员 |
| 评估提议、确认转需求、直接导入已确认需求、修改需求内容和文档关联、上传文档 | 产品经理或管理员 |
| 拆分并指派任务、应用任务规划或调整需求承诺排期 | 主开发或管理员 |

如果当前账号不够，告诉用户需要换哪个账号登录，不要绕开限制。

## 第 1 步：读文档，并上传到平台

**文档体系约定。** 平台据此识别章节，需求才能按章节关联：
- PRD（产品需求文档，`.md`）：章节标题带编号，例如 `## 3.1 渠道〔RES-3.1〕`，编号取〔〕里的内容。
- 技术方案（`.md`）：用数字章节号，识别为 `§9`、`§16.1`。
- 验收用例（`.feature`）：每个 `Scenario`（场景）上一行的第一个 `@标签` 就是用例编号，例如 `@GW-AC-07`。
- 排期规划：节点日期、团队配置、所在地和假期、预设可砍项、外部依赖。这份一定要读，排期的约束都在里面。

```sh
xinghe document list --project <编号>
xinghe document upload --project <编号> --file PRD/模块/M1-网关.md --type PRD
xinghe document upload --project <编号> --file PRD/验收/M1-网关.feature --type 验收用例
xinghe document upload --project <编号> --document <已有文档编号> --file <新版本文件> --note "说明"   # 已有文档传新版本
```

上传后用 `document list`（文档列表）检查每份文档的 `sections`（章节）是否识别出了章节。产品需求文档没有〔编号〕时，说明当前无法按章节关联；可以先使用全文关联，或由用户决定是否补编号。

读完文档后，列出：
- 事实：范围、节点和日期、团队、可砍项；
- 你的假设；
- 待确认的问题。

问题交给用户，不要自己编答案。

## 第 2 步：拆需求

**粒度：需求 = 一个可以单独验收的功能块，通常就是「一个模块在一个交付节点的交付内容」，约 1～2 周工作量。**

- 不要一个 PRD 章节一条需求。章节级的工作是任务，由主开发拆。
- 同一模块的大部分内容在同一个节点交付时，合成一条；描述里按节点列出覆盖的章节。
- 预设可砍项（例如视频生成、某种语言的界面）必须单独成一条需求，砍掉时才不影响别的。
- 横切的非功能要求（性能、安全、可观测性、开源发布、测试基础设施）各自成一条。
- 一个中型模块化 PRD（10 个左右模块）通常拆出 20～40 条需求；少于 10 条或多于 60 条，都要回头检查粒度。

**每条需求的字段**（完整格式见 `references/requirements.example.json`（需求数据示例））：

| 字段 | 写法 |
| --- | --- |
| `title`（标题） | 功能块名称，20 字以内，例如「文本协议网关」「计价、预扣与结算」 |
| `description`（背景与目标） | 必填。一两句背景、目标与范围，加上覆盖的产品需求章节、交付节点 |
| `acceptance`（验收标准） | 必填。用例编号、名称和节点；没有 .feature 文件时，写可以检验的验收标准 |
| `priority`（优先级） | P0（最高优先级）：核心链路或不可砍；P1（高优先级）：本期核心价值；P2（普通优先级）：可延后或预设可砍 |
| `source`（来源） | 文档名和章节，例如「PRD M1〔GW-2、GW-3〕」 |
| `docRefs`（文档关联） | `[{"document":"M1.md","type":"PRD","sections":["GW-2","GW-3.1"]}]`；字段依次为文档名、类型、章节编号。空章节数组表示全文引用 |
| `acceptanceCases`（验收用例编号） | 用例编号列表，例如 `["GW-AC-01","GW-AC-08"]` |
| `dependencyIds`（前置需求编号） | 仅已确认需求支持；只填真正阻塞开工的前置需求。拿不准就不填，在汇报里说明 |

提议可先缺少背景或验收内容，确认前必须补齐；其核心字段与需求相同，但不接收研发协作、依赖和排期字段。`proposerName`（提出人）默认采用当前账号姓名。

**覆盖检查：** PRD 里每个带编号的章节，都应该被某条需求引用；没被引用的，要在汇报里列出，并说明原因（不在本期范围 / 待确认）。

## 第 3 步：导入提议或已确认需求

把清单写成 JSON（结构化数据）数组。每条加一个 `key`（本地标识），方便后面对应编号。尚待确认时：

```sh
xinghe proposal import --project <编号> --data-file proposals.json --dry-run
xinghe proposal import --project <编号> --data-file proposals.json
```

用户已明确确认清单，且背景与目标、验收标准完整时，可直接导入“已确定”需求：

```sh
xinghe requirement import --project <编号> --data-file reqs.json --dry-run   # 看新建 / 已存在 / 警告
xinghe requirement import --project <编号> --data-file reqs.json            # 真正导入
```

- 预检的 `warnings`（警告）会指出缺失的文档章节或用例。修正引用问题后再导入；直接导入需求时缺少背景或验收会被拒绝。
- 导入只跳过当前项目已有的同名记录，不更新其内容，也不保证并发幂等。网络中断后先查列表，核对已创建项及重名内容，再决定重跑；不要同时执行同一批导入。
- 输出的 `items`（结果项）里有每个 `key`（本地标识）对应的记录编号。提议编号不能用于任务计划；确认后用返回的关联需求编号。
- 对已导入的提议，产品经理评估并取得用户确认后逐条确认；每次使用刚查询的 `version`（版本号）：

```sh
xinghe proposal get <提议编号>
xinghe proposal approve <提议编号> --version <当前版本>
```

需要补充时用 `proposal update`（修改提议），可通过数据文件修改背景、验收标准、文档关联及 `decisionReason`（评估说明）。确认保留提议、来源与关联文档；历史早期需求确认后保留原编号。已转需求的内容从关联需求修改。

## 第 4 步：拆任务

**粒度：任务 = 2～3 天（12～24 小时）的一个可演示成果。** 任务是用来管进度的，不是操作步骤清单。拆得太碎，主开发拆分、开发点状态、他人验收的沟通成本都会翻倍，领导看全局排期时也只会看到一堆琐事。

- 每人每周大约 1～2 个任务。单个任务上限约 30 小时，超过就按可演示的结果拆开。
- 不拆半天的任务。「联调」「自测」「写测试」都并入对应的实现任务（标题写「……（含场景联调）」）。
- 同一需求、同一个人、同一阶段的工作合成一个任务。
- 只有带固定截止日的交付物才单列，即使只有 1 天。例如选型验证报告、接口契约定稿。
- 标题写「做成什么」，例如「快照消费：整版原子替换、缓存目录模式与冷加载（含场景联调）」。`desc`（任务说明）里写对应的章节编号和验收用例编号。
- 按用户确认的分工分配负责人。跨专业的小块，比如某个页面需要的接口，可以交给做页面的人，在任务说明里注明由对口的人评审。
- 估时以已确认的团队工具与效率为前提，不默认使用人工智能后就能缩短工时。计费、鉴权、流式处理、凭证这类要人工逐行审查的模块，要多留余量。

拆完后自查：平均工时应在 12～24 小时之间，8 小时以下的任务应该只是少数带截止日的交付物。`plan preview`（任务规划预览）输出的 `granularity`（任务粒度）会给出这两项统计。

## 第 5 步：排期

计划文件格式见 `references/plan.example.json`（任务规划示例），要点如下：

- `startDate`（开始日期）：下一个工作日。`holidays`（假期）：团队所在地的公众假期，不默认用中国假期，不确定就问。`extraWorkdays`（额外工作日）：调休上班日。
- `capacityHours`（每日产能）：每人每天有效开发时间，默认 7 小时。`capacityOverrides`（时段产能覆盖）：只在规划文档写明加班的冲刺期使用。
- `phases`（交付节点顺序）：比如 `["N0","S","N1","N2","N3","N4","cut"]`，其中 `cut`（可砍项）放最后。`phaseDeadlines`（节点截止日期）用来检查能否赶上。
- `after`（前置任务）：跨人的硬前置，比如契约定稿要等契约草案。只在确实需要时使用。
- `respectExistingLoad`（考虑已有负荷）：默认 `true`（是），新工作接在每个人已有未完成任务之后。如果新项目优先级更高，问过用户后设为 `false`（否），并给出开始日期。
- `owners`（负责人别名）：分工映射，例如 `{"A":"yanp","B":"zeng","C":"wu-dev"}`。
- `acceptanceBufferDays`（验收缓冲工作日）：默认 1 天，只计入建议交付日期，不会自动写入需求承诺。

```sh
xinghe plan preview --project <编号> --data-file plan.json
```

看预览结果时检查下面几项，然后调整计划、再次预览：

- `late`（晚于项目目标）：哪些需求的建议结束日晚于项目目标日期。
- `phaseLate`（晚于节点）：哪些节点赶不上。
- `load`（人员负荷）：每人的总工时和排到哪天。结合专长和依赖检查是否不均衡，不为追求结束日期相同而强行调换工作。
- `skipped`（跳过项）：已有其他任务的需求会被跳过，不会覆盖。
- `notConfirmed`（尚未确认）与 `blocked`（不可排期项）：历史早期需求、已结束需求等不能应用计划，必须先处理或移出计划。存在不可排期项时，应用会整批拒绝，不会先为这些需求创建任务。
- 每条需求的 `planStart` / `planEnd`（建议开始 / 结束日期）与 `commitmentStart` / `commitmentEnd`（现有承诺开始 / 结束日期）要分别核对；`beyondCommitment`（晚于现有承诺）提示建议日期与承诺的冲突。

**把结论给用户看**，内容包括：每人工时和结束日期、各节点能否赶上、超期项和原因、可选的应对办法（调整优先级、砍掉预设可砍项、增加人手、接受延期）。由用户决定后，再用主开发或管理员账号写入：

```sh
xinghe plan apply --project <编号> --data-file plan.json            # 晚于项目目标或现有承诺时会拒绝写入
xinghe plan apply --project <编号> --data-file plan.json --force    # 用户接受冲突后再加
```

`plan apply`（应用任务规划）只为已确认且未结束的需求批量创建任务，设置主责开发（工时最多的人）和协作人，研发阶段由后端根据任务自动同步。已有承诺日期及基线保持不变；没有承诺时也不自动创建。建议区间按任务最早开始、最晚结束加验收缓冲计算。`--force`（接受冲突）只允许本次任务计划继续执行，不代表调整承诺或绕过确认、权限限制。

同一份计划重跑不重复创建任务，已完成的规划不再写入，也不覆盖人工改期。批量创建的提交编号稳定，但整份多需求计划不是单一事务；中断后先查询已处理项再决定重跑。

用户另外授权设定或修改承诺日期时，使用专用命令：

```sh
xinghe requirement get <需求编号>
xinghe requirement schedule <需求编号> --version <当前版本> --start 2026-10-05 --end 2026-10-09
# 多需求承诺改期先预览，再使用同一文件和预览令牌应用
xinghe schedule preview --project <编号> --data-file changes.json
xinghe schedule apply --project <编号> --data-file changes.json --token <预览令牌> --reason "已确认的承诺改期原因"
```

`changes.json`（承诺改期文件）每项包含 `requirementId`（需求编号）、`version`（当前版本）、`planStart`（承诺开始日期）、`planEnd`（承诺结束日期）。此时日期字段表示要写入的承诺，与任务规划中的建议日期含义不同。首次承诺按平台规则建立基线，后续改期应说明原因。

## 第 6 步：核对与汇报

```sh
xinghe schedule list --kind requirement --project <编号>
xinghe schedule list --kind requirement --basis commitment --project <编号>
xinghe plan preview --project <编号> --data-file plan.json   # 已写入的需求显示 alreadyCreated
```

需求排期默认按有效任务汇总的研发区间筛选，没有任务日期才回退到承诺，并输出日期来源和承诺信息；`--basis commitment`（按承诺日期）单独查看承诺。预览中的 `alreadyCreated`（任务已创建）用于核对重复执行状态，不代表人工验收已完成。

请用户在网页的「全局排期」里看一眼效果。给用户的汇报包含：

1. 写入了什么：多少条需求、多少个任务，每人多少小时、排到哪天。
2. 各节点对照表：节点日期、任务预计最晚完成日期、建议交付日期、现有承诺日期；尚未发生的完成日期不能写成实际完成日期。
3. 超期或有风险的项，以及原因。
4. 做过的假设：分工、产能、假期、估时依据。
5. 还在等用户确认的事项：提议采纳、承诺日期、可砍项的决定、有疑问的章节。

需要验收退回或重新打开时，不直接修改研发阶段。使用 `requirement return`（退回研发）或 `requirement reopen`（重新打开），提供刚查询的版本和真实原因；退回时用 `taskIds`（返工任务编号）指定任务：

```sh
xinghe requirement return <需求编号> --version <当前版本> --reason "验收未通过的具体原因" --data '{"taskIds":["t-实际编号"]}'
xinghe requirement reopen <需求编号> --version <当前版本> --reason "重新打开的具体原因"
xinghe requirement history <需求编号>
xinghe task history <任务编号>
```

`requirement history`（需求历史）与 `task history`（任务历史）用于核对操作结果；适用阶段和权限由后端检查。

## 出错时

| 现象 | 处理 |
| --- | --- |
| `FORBIDDEN`（无权限） / 403 | 账号角色不够：评估和需求内容由产品经理维护，拆分和排期由主开发处理 |
| `VERSION_CONFLICT`（版本冲突） / 409 | 别人刚改过记录。重新查询，核对差异与原意，再使用最新版本修改；不要只替换版本号强行覆盖 |
| `TRANSITION_GATE`（流转条件未满足） | 按提示补齐背景、验收标准、任务准备或验收条件。禁止用修改状态绕过自动阶段同步 |
| 网络中断 | 先查询列表、详情与历史。导入只有同名跳过机制，不保证并发幂等；确认已处理项后再重跑。任务规划核对后可用同一文件重跑；不要盲目重试单条创建 |
| 任务已经有人开始做 | 不要重建。经授权用 `task update`（修改任务）调整，或请主开发在网页上改；重跑计划不会替代人工改期 |
