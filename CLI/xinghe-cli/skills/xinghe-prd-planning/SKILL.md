# 从 PRD 到需求、任务与排期（星河研发台）

目标：用户把 PRD 交给你，你交还一套**能直接用来管理进度**的需求、任务和排期，已经写入星河研发台，并附一份如实的汇报（谁排到哪天、哪些节点赶不上、哪些假设需要确认）。

所有读写都通过 `xinghe` 命令行完成，不直接改数据库。先运行 `xinghe --help` 和 `xinghe schema`，看当前版本支持的命令和字段。

## 硬规则

1. **不猜编号。** 项目、成员、需求、文档的编号都要从 `project list`、`project members`、`requirement list`、`document list` 的输出里取。
2. **遇到下面五件事必须停下来问用户**，不要自己决定：
   - 文档对应哪个项目。一份文档可能要拆成几个项目，比如一份算法方案同时对应「评估方」和「执行方」两个项目。
   - 成员分工：谁负责哪个专业方向。项目成员只记录了角色（主开发 / 开发 / 测试），没有专长。规划文档如果写了「工程师 A / B / C」，要问清楚分别对应哪个账号。
   - 多个项目时间重叠时，先保哪个。
   - 需求清单：导入前把需求表给用户过目。
   - 写入排期前：把 `plan preview` 的结论给用户看，尤其是超期和超载。
3. **需求一律从「未确定」创建。** 用户明确确认后，才流转到「待评审 → 已确定」。
4. **如实报告超期和超载。** 不要为了排进节点而悄悄压缩工时、删减范围或假设加班。只有规划文档写明了加班安排，才能在冲刺期提高每日产能，并在汇报里写明。
5. **写入前确认目标环境。** 用 `xinghe config show --profile <环境>` 核对地址，并向用户说明「将写入 <地址>」。正式环境和本机环境分别用不同的 profile（例如 `production`、`local`）。第一次在正式环境操作时，建议先在本机环境完整演练一遍。
6. **写操作先预览。** `requirement import --dry-run` 和 `plan preview` 看过、用户同意后，才执行真正的写入。

## 第 0 步：准备

```sh
xinghe config show --profile <环境>          # 确认连的是哪个平台
xinghe auth me --profile <环境>              # 确认登录账号
xinghe project list --profile <环境>
xinghe project members <项目编号> --profile <环境>
xinghe schedule list --kind requirement --profile <环境>   # 了解现有排期
```

登录由用户在自己的终端完成：`xinghe auth login --username <账号>`。不要索要或转述密码。

**账号权限决定能做哪一步：**

| 步骤 | 需要的项目角色 |
| --- | --- |
| 上传文档、导入需求、修改需求内容和文档关联、流转到「待评审 / 已确定」 | 产品经理或管理员 |
| 拆分并指派任务、写入需求排期（`plan apply`） | 主开发或管理员 |

如果当前账号不够，告诉用户需要换哪个账号登录，不要绕开限制。

## 第 1 步：读文档，并上传到平台

**文档体系约定。** 平台据此识别章节，需求才能按章节关联：
- PRD（`.md`）：章节标题带编号，例如 `## 3.1 渠道〔RES-3.1〕`，编号取〔〕里的内容。
- 技术方案（`.md`）：用数字章节号，识别为 `§9`、`§16.1`。
- 验收用例（`.feature`）：每个 `Scenario` 上一行的第一个 `@标签` 就是用例编号，例如 `@GW-AC-07`。
- 排期规划：节点日期、团队配置、所在地和假期、预设可砍项、外部依赖。这份一定要读，排期的约束都在里面。

```sh
xinghe document list --project <编号>
xinghe document upload --project <编号> --file PRD/模块/M1-网关.md --type PRD
xinghe document upload --project <编号> --file PRD/验收/M1-网关.feature --type 验收用例
xinghe document upload --project <编号> --document <已有文档编号> --file <新版本文件> --note "说明"   # 已有文档传新版本
```

上传后用 `document list` 检查每份文档的 `sections` 是否识别出了章节。PRD 没有〔编号〕时，告诉用户需求将无法按章节关联，问是否先补编号。

读完文档后，列出：
- 事实：范围、节点和日期、团队、可砍项；
- 你的假设；
- 待确认的问题。

问题交给用户，不要自己编答案。

## 第 2 步：拆需求

**粒度：需求 = 一个可以单独验收的功能块，通常就是「一个模块在一个交付节点的交付内容」，约 1～2 周工作量。**

- 不要一个 PRD 章节一条需求。章节级的工作是任务，由主开发拆。
- 同一模块的大部分内容在同一个节点交付时，合成一条；描述里按节点列出覆盖的章节。
- 预设可砍项（例如视频生成、某种语言的界面）必须单独成一条需求，砍掉时才不影响别的。
- 横切的非功能要求（性能、安全、可观测性、开源发布、测试基础设施）各自成一条。
- 一个中型模块化 PRD（10 个左右模块）通常拆出 20～40 条需求；少于 10 条或多于 60 条，都要回头检查粒度。

**每条需求的字段**（完整格式见 `references/requirements.example.json`）：

| 字段 | 写法 |
| --- | --- |
| `title` | 功能块名称，20 字以内，例如「文本协议网关」「计价、预扣与结算」 |
| `description` | 一两句范围说明，加上「覆盖的 PRD 章节」列表（每行：〔编号〕标题（节点 · 日期）），再加交付节点 |
| `acceptance` | 「按以下 N 条验收用例逐条验收：」加上用例编号、名称和节点。没有 .feature 文件时，写可以检验的验收标准 |
| `priority` | P0：核心链路或写明「不可砍」；P1：本期核心价值；P2：可延后或预设可砍 |
| `source` | 文档名 + 章节，例如「PRD M1〔GW-2、GW-3〕」 |
| `docRefs` | `[{"document":"文件名","type":"PRD","sections":["GW-2","GW-3.1"]}, {"document":"M1.feature","type":"验收用例","sections":[…]}]` |
| `acceptanceCases` | 用例编号列表，例如 `["GW-AC-01","GW-AC-08"]` |
| `dependencyIds` | 只填真正阻塞开工的前置需求（它未完成时这条不能开工）。拿不准就不填，在汇报里说明 |

**覆盖检查：** PRD 里每个带编号的章节，都应该被某条需求引用；没被引用的，要在汇报里列出，并说明原因（不在本期范围 / 待确认）。

## 第 3 步：导入需求

把需求写成 JSON 数组。每条加一个 `key`，作为本地标识，方便后面对应编号。

```sh
xinghe requirement import --project <编号> --data-file reqs.json --dry-run   # 看新建 / 已存在 / 警告
xinghe requirement import --project <编号> --data-file reqs.json            # 真正导入
```

- 预检的 `warnings` 会指出找不到的章节、找不到的用例、缺少验收标准。先修正，再导入。
- 导入按标题去重，网络中断后可以直接重跑同一命令。
- 输出的 `items` 里有每个 `key` 对应的需求编号，排期计划要用这些编号。
- 用户确认需求后，逐条流转（每次都用刚查到的 version）：

```sh
xinghe requirement get <需求编号>                                        # 取 version
xinghe requirement update <需求编号> --version <v> --status 待评审
xinghe requirement update <需求编号> --version <v+1> --status 已确定
```

## 第 4 步：拆任务

**粒度：任务 = 2～3 天（12～24 小时）的一个可演示成果。** 任务是用来管进度的，不是操作步骤清单。拆得太碎，主开发拆分、开发点状态、他人验收的沟通成本都会翻倍，领导看全局排期时也只会看到一堆琐事。

- 每人每周大约 1～2 个任务。单个任务上限约 30 小时，超过就按可演示的结果拆开。
- 不拆半天的任务。「联调」「自测」「写测试」都并入对应的实现任务（标题写「……（含场景联调）」）。
- 同一需求、同一个人、同一阶段的工作合成一个任务。
- 只有带固定截止日的交付物才单列，即使只有 1 天。例如选型验证报告、接口契约定稿。
- 标题写「做成什么」，例如「快照消费：整版原子替换、缓存目录模式与冷加载（含场景联调）」。`desc` 里写对应的章节编号和验收用例编号。
- 按用户确认的分工分配负责人。跨专业的小块，比如某个页面需要的接口，可以交给做页面的人，在 `desc` 里注明由对口的人评审。
- 估时以团队使用 AI 编程为前提，给经验值。计费、鉴权、流式处理、凭证这类要人工逐行审查的模块，要多留余量。

拆完后自查：平均工时应在 12～24 小时之间，8 小时以下的任务应该只是少数带截止日的交付物。`plan preview` 输出的 `granularity` 会给出这两项统计。

## 第 5 步：排期

计划文件格式见 `references/plan.example.json`，要点如下：

- `startDate`：下一个工作日。`holidays`：团队所在地的公众假期（按规划文档里写的所在地，不要默认用中国假期），不确定就问。`extraWorkdays`：调休上班日。
- `capacityHours`：每人每天有效开发时间，默认 7。`capacityOverrides`：只在规划文档写明加班的冲刺期使用。
- `phases`：按节点顺序排列，比如 `["N0","S","N1","N2","N3","N4","cut"]`。预设可砍项放最后一个阶段，砍掉时不影响别的任务。`phaseDeadlines` 填各节点日期，用来检查能否赶上。
- `after`：跨人的硬前置，比如契约定稿要等契约草案。只在确实需要时使用。
- `respectExistingLoad`：默认 true，新工作接在每个人已有未完成任务之后。如果新项目优先级更高，问过用户后设为 false，并给出 `startDate`。
- `owners`：分工别名，例如 `{"A":"yanp","B":"zeng","C":"wu-dev"}`。

```sh
xinghe plan preview --project <编号> --data-file plan.json
```

看预览结果时检查下面几项，然后调整计划、再次预览：

- `late`：哪些需求的计划结束日晚于项目目标日期。
- `phaseLate`：哪些节点赶不上。
- `load`：每人的总工时和排到哪天。几个人的结束日期应该大致相近。如果有人明显晚很多，把边界清晰的任务转给最先空出来的人，并写明原因。
- `skipped`：已有其他任务的需求会被跳过，不会覆盖。
- `notConfirmed`：还没有确认的需求，只会写入任务和计划日期。

**把结论给用户看**，内容包括：每人工时和结束日期、各节点能否赶上、超期项和原因、可选的应对办法（调整优先级、砍掉预设可砍项、增加人手、接受延期）。由用户决定后，再用主开发或管理员账号写入：

```sh
xinghe plan apply --project <编号> --data-file plan.json            # 有超期需求时会拒绝写入
xinghe plan apply --project <编号> --data-file plan.json --force    # 用户接受超期后再加
```

`plan apply` 会为每条需求批量创建任务，设置主责开发（工时最多的人）和协作人，写入计划起止日期（最早开始到最晚结束，再加 1 个工作日验收缓冲），把「已确定」的需求流转为「已排期」。首次排期的日期自动成为基线。重跑同一份计划不会重复创建任务。

## 第 6 步：核对与汇报

```sh
xinghe schedule list --kind requirement --project <编号>
xinghe plan preview --project <编号> --data-file plan.json   # 已写入的需求显示 alreadyCreated
```

请用户在网页的「全局排期」里看一眼效果。给用户的汇报包含：

1. 写入了什么：多少条需求、多少个任务，每人多少小时、排到哪天。
2. 各节点对照表：节点日期和实际最晚完成日期。
3. 超期或有风险的项，以及原因。
4. 做过的假设：分工、产能、假期、估时依据。
5. 还在等用户确认的事项：需求状态、可砍项的决定、有疑问的章节。

## 出错时

| 现象 | 处理 |
| --- | --- |
| `FORBIDDEN` / 403 | 账号角色不够：内容和文档关联由产品经理改，拆分和排期由主开发做 |
| `VERSION_CONFLICT` / 409 | 别人刚改过这条记录。重新 `get` 取最新 version 后再改，不要强行覆盖 |
| `TRANSITION_GATE` | 流转条件不满足，比如没有验收标准不能「已确定」，拆分没完成不能「已排期」。按提示补齐 |
| 网络中断 | `requirement import` 和 `plan apply` 可以直接重跑同一命令；单条 `requirement create` 不要重跑，先 `requirement list` 查一下 |
| 任务已经有人开始做 | 不要重建。用 `task update` 调整，或请主开发在网页上改 |
