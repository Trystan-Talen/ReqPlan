# 星河研发台 · 服务器版

本目录为服务器版源码。本机正式维护入口位于桌面“需求管理3/星河研发台_服务器版”；工作区副本用于本次构建与验证。业务数据、账号、权限、会话和附件由服务端保存；请通过启动器或已部署站点使用。旧单文件页面和桌面原项目作为历史资料保留，浏览器里的旧编辑不会自动同步。

本次修复内容见 [修复清单](修复清单.md)，验证范围与部署检查见 [验收说明](验收说明.md)。旧《验收与交付说明》和旧测试输出不代表本次验收结果。

## 本次可用功能

- 项目、需求、任务、成员、里程碑与周/月/季度/完整周期排期；按项目隔离权限。
- 需求批量拆分任务：整批校验、事务提交、重复提交去重；失败保留当前账号的会话草稿。
- 附件版本链、历史版本下载与文本对照；相同需求内同名同类型的上传形成新版本，旧下载地址保留。
- 需求旧历史与新增记录合并展示，修改前后差异、基线日期和改期偏移可查看。
- 前后端共用流程规则，界面显示当前阶段可执行操作及受阻原因；服务端再次校验权限和条件。
- 需求与任务前置依赖：检查跨项目、未知引用、自身依赖和环路；前置事项未完成时阻止开始开发。
- 批量调整需求排期：先预览、再整批提交；冲突阻止整批写入，超项目目标日期需明确确认。
- 个人工作台、站内交付与验收提醒、跨项目交付风险和最近八周统计。提醒在打开或刷新页面时更新，已读不代表问题已解决；未配置邮件或外部消息推送。
- 自动备份、管理员备份状态、手动触发、隔离恢复演练与持续集成配置。

原始脱敏快照保留 3 个项目、55 条需求、79 条任务、6 位人员及 2 份当前附件。这个数量是随包迁移基线；运行中数据库可能已有新编辑，不能用基线覆盖它。附件版本历史由单独补录脚本核对。

## 启动与账号

在 macOS（苹果电脑系统）访达中双击 `启动星河研发台.command`（本机启动文件），或在本目录运行：

```sh
npm run dev
```

网页和接口分别使用系统分配的空闲端口，启动器显示实际地址并打开浏览器。保持终端窗口开启，按控制键加 C 停止。端口会变化；`backend/var/local-server.json`（本机运行状态）记录当前地址，不保存密码或初始化令牌。

首次没有管理员时，在网页填写账号、姓名及密码，最低 **6 个字符**。已有管理员时沿用原账号；当前本机管理员登录名为 `admin`（管理员账号），新环境以首次填写的名称为准。空数据库可导入随包快照，非空库不会被清空重建。

忘记管理员密码时，保持服务运行，双击 `重置管理员密码.command`（密码恢复启动文件）。它核验运行实例后打开一次性网页，输入两次至少 6 位的新密码。链接有效期 30 分钟，签发时撤销旧密码与会话，保留人员编号和业务关联。多名管理员可运行：

```sh
npm run recover:admin -- --username admin
```

本机启动器继续兼容 22.23 及以上 22 系列、24.15 及以上 24 系列。当前测试及接口镜像以 Node.js 24.19.0（运行环境）为准。源码无第三方运行依赖，测试不需要安装额外依赖。

## 角色与数据库第 3 版升级

角色分两层，完整规则见 [改版方案](改版方案.md)，共享实现位于 `frontend/workflow.js`：

| 层级 | 角色 | 能做什么 |
| --- | --- | --- |
| 系统 | 系统管理员 | 账号、备份、操作记录、创建项目；在任何项目中拥有全部权限 |
| 系统 | 管理层 | 无需加入项目即可只读查看全部项目，不能修改任何内容 |
| 项目 | 产品经理 | 维护需求内容与文档、组织评审、终止需求、确认排期 |
| 项目 | 主开发 | 指定主责开发、拆分和分派任务、终止和归档任务、安排排期 |
| 项目 | 开发 | 推进本人任务；在参与的需求下为自己补充任务（主开发会收到提醒） |
| 项目 | 测试 | 验收或退回任务和需求（退回需填写原因） |
| 项目 | 观察者 | 只读 |

项目负责人必须是该项目的产品经理或主开发，由负责人或系统管理员管理成员。任务必须关联需求。

第 3 版取消「项目经理」角色。旧数据库必须先按确认过的计划迁移，否则服务拒绝打开并提示未指定的成员，不做任何修改。迁移计划位于 `backend/migrations/role-migration-2026-09.json`。先停止服务，再执行：

```sh
npm run migrate:roles
npm run migrate:roles -- --apply
```

第一条只预检，列出每位成员的角色变化和业务数据数量；第二条先在数据库旁的 `backups/` 目录生成完整性校验通过的备份，再迁移，并核对项目、需求、任务、附件和账号数量前后一致。其他数据库可用 `--db 路径`、`--plan 计划文件` 和 `--backup-dir 目录` 指定。

## 服务器部署

本方案使用单台服务器上的 SQLite（轻量关系数据库）持久卷，适用于内部团队单实例部署。数据库不要放到网络共享目录，也不要让多个主机同时写同一文件。容量和高并发压力尚须在目标环境测量。

准备 Linux（服务器系统）、Docker Compose（容器编排工具）、真实域名及 HTTPS（加密连接）网关后：

1. 将本目录放进服务器私有目录。
2. 复制 `.env.example`（配置示例）为 `.env`（实际配置），填写 `PUBLIC_ORIGIN`（实际加密站点地址）。首次初始化填写 `XINGHE_SETUP_TOKEN`（一次性初始化凭证），可用下面命令生成并私下保存，管理员建立后删除。

```sh
node -e "process.stdout.write(require('node:crypto').randomBytes(32).toString('base64url'))"
```

3. 构建镜像。仅首次空库需要导入；升级现有实例直接重建并重启，先完成备份核验。

```sh
docker compose config --quiet
docker compose build
docker compose run --rm api node backend/scripts/import-legacy.mjs --db /app/data/xinghe.sqlite --dry-run
docker compose run --rm api node backend/scripts/import-legacy.mjs --db /app/data/xinghe.sqlite
docker compose up -d
docker compose ps
```

4. 将加密网关转发到 `http://127.0.0.1:8080`（本机网页容器入口）。接口容器不向宿主机发布端口。
5. 首次打开实际站点，在地址末尾追加 `/#setup=你的初始化凭证`（初始化入口片段），设置账号及至少 6 位密码；已有管理员直接登录。

`xinghe-data`（数据持久卷）保存业务数据、附件、会话、审计和主备份。重建镜像不会清空卷；升级不要使用删除卷的命令。数据结构升级保留原附件编号与内容，不能用旧版程序降级打开升级后的库。

接口镜像固定为 `node:24.19.0-bookworm-slim`（运行环境镜像），包含 `/app/backend`（后端目录）、`/app/frontend/workflow.js`（共享规则）、`/app/package.json`（模块声明）及 `/app/deploy/admin-recovery.mjs`（管理员救援）。网页镜像包含完整前端文件。完整自动测试须在完整源码目录运行；接口镜像不包含全部网页及本机启动测试所需文件。

## 自动备份与恢复演练

服务启动后自动安排备份，后台工作线程执行快照及完整性检查。已有近期备份时按上次时间续排。失败记录安全错误码并重试；管理员可查看状态或立即备份。

| 配置字段 | 默认值 | 含义 |
| --- | --- | --- |
| `BACKUP_ENABLED`（自动备份开关） | `1` | 设为 `0` 停用 |
| `BACKUP_DIRECTORY`（主备份目录） | 数据库旁的备份目录 | 容器固定为 `/app/data/backups`（数据卷内目录） |
| `BACKUP_INTERVAL_HOURS`（备份间隔小时） | `24` | 正常备份间隔 |
| `BACKUP_INITIAL_DELAY_SECONDS`（首轮等待秒） | `60` | 首轮最早触发时间 |
| `BACKUP_RETRY_MINUTES`（失败重试分钟） | `30` | 本地或第二目的地失败后的重试间隔 |
| `BACKUP_RETAIN_COUNT`（保留份数） | `30` | 只清理自动生成的备份；手动备份不删 |
| `BACKUP_SECONDARY_DIRECTORY`（第二备份目录） | 空 | 可选；容器必须另行挂载可写目录 |

备份包含已经提交的预写日志数据。检查通过后才以新文件发布，已有目标拒绝覆盖；每份快照是可独立读取的数据库文件。第二目录复制已完成的同一快照，状态单独记录。仅配置第二目录或看到不同设备编号都不能证明完成物理异地备份；需要运维确认实际设备、位置、权限与可恢复性。

手动备份及隔离恢复演练：

```sh
npm run backup -- /私有备份目录/新备份.sqlite
npm run restore:check -- /私有备份目录/新备份.sqlite
```

`backup`（备份命令）默认读取本机业务库，也可设置 `DATABASE_PATH`（数据库路径）。`restore:check`（恢复演练命令）只在临时目录生成副本，检查完整性、外键、结构、数据数量及事务写入回滚，结束后清理；它不会替换运行中的数据库。

容器对应命令：

```sh
docker compose exec api node backend/scripts/backup.mjs
docker compose exec api node backend/scripts/restore-check.mjs /app/data/backups/实际备份文件.sqlite
```

真正恢复时先停止接口服务，保留当前数据库及其日志文件，将核验通过的快照放进全新目录，挂载该目录后启动并核对业务。保留旧卷用于回退，不在线覆盖已打开的数据库，也不混用旧日志文件。

## 补录原附件历史

附件补录读取原附件 Git（版本管理）历史，匹配已有需求，按内容去重，并记录来源。默认只预检；显式使用 `--apply`（确认执行参数）才会写入，写入前自动产生独立备份。补录不会替换已有当前附件。

在具备 Node.js（运行环境）及 Git（版本管理工具）的维护主机上执行。接口运行镜像未安装版本管理工具，不能直接照搬到该容器运行。原附件目录和目标数据库分别指定，目标数据库及备份不能放进原版本库。

```sh
npm run import:attachment-history -- --source-files /原项目/data/files --database /当前项目/backend/var/xinghe.sqlite
npm run import:attachment-history -- --source-files /原项目/data/files --database /当前项目/backend/var/xinghe.sqlite --apply
```

先核对预检中的新版本、映射、已导入、未匹配需求和忽略文件数量。遇到疑似凭证、路径越界、不支持类型或文件超限时会拒绝；在独立副本处理后重新预检。重复执行不会重复插入已补录版本。历史来源及版本时间会展示，旧文件不会伪装成刚上传的新文件。

## 从原系统准备最新业务快照

原系统若继续录入，首次上线前先停写再准备最新快照：

```sh
node backend/scripts/prepare-legacy.mjs --source /原项目/data/db.json --output backend/seed-latest/legacy.json --dry-run
node backend/scripts/prepare-legacy.mjs --source /原项目/data/db.json --output backend/seed-latest/legacy.json
node backend/scripts/import-legacy.mjs --source backend/seed-latest/legacy.json --db backend/var/xinghe.sqlite --dry-run
```

`--dry-run`（仅预检参数）不导入数据。核对通过后，仅向空目标库去掉此参数执行导入。已有业务的数据库拒绝另一份快照，不能清空后重导。测试命令和持续集成不会调用 `reseed`（重填业务数据脚本）。

## 维护与验证

```sh
npm test
XINGHE_HTTP_SOCKET=1 node --test backend/tests/http.test.mjs
```

第一条执行完整隔离测试，第二条额外验证实际临时端口传输，需要环境允许监听。持续集成配置固定同一 24.19.0 运行环境，先检查源文件语法，再运行完整测试，使用内存数据库。仓库以本目录为根可直接使用；若以外层工作区为根，应把持续集成文件放到仓库根的 `.github/workflows/`（工作流目录），流程会自动查找项目。

当前交付包含配置与源码；远程持续集成、容器构建、生产域名、证书与异地备份的实际状态，以 [验收说明](验收说明.md) 为准。

服务器管理员救援：

```sh
docker compose exec api node deploy/admin-recovery.mjs --db /app/data/xinghe.sqlite --url https://实际站点 --username admin --print-link
```

`--print-link`（显示一次性链接参数）只供对应管理员本人使用，不写入共享日志。站点不能访问时，可在交互终端使用 `accounts.mjs`（账号维护脚本）重设临时密码，登录后再次修改。

旧模型凭证没有迁入本版；撤销状态仍需凭证所有者在原服务商核实。模型自动分析尚未接入，功能点分层按之前约定继续后排。后续维护遵守 `AGENTS.md`（项目约定文件）中的真实数据保留要求。
